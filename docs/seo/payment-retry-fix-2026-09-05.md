## Change and guarantees

The old callback updated `payments.status/paid_at`, then separately fetched package generations and called `increment_paid_generations`. Every signed replay credited again; a failed increment could still return `OK` after storing `paid`.

The new `confirm_package_payment(uuid, integer, numeric)` RPC locks the payment row with `FOR UPDATE`. It validates the stored invoice and amount before considering a duplicate. Only a clean pending row can transition to paid. Package quantity is read under a row lock; paid status, `paid_at`, a positive `credited_generations` receipt and the user balance increment commit together. Missing/invalid balance, missing/invalid package, SQL error or integer overflow aborts the transaction. Concurrent different payments to the same user use PostgreSQL's locked arithmetic update, avoiding lost increments.

A fulfilled payment returns `already_paid` without touching the balance or `paid_at`, even if the catalog later changes. A payment still marked pending but carrying a timestamp/receipt fails closed. The callback returns `OK{InvId}` only after `credited` or `already_paid`; invalid payment parameters return 400, operational/uncertain/legacy fulfillment errors return 503 so the provider can retry. Repeated permanent 503 errors require operator reconciliation; retries alone cannot resolve historical ambiguity.

The RPC is `SECURITY INVOKER` with an empty `search_path` and qualified tables. Only `service_role` receives EXECUTE; PUBLIC, anon and authenticated are explicitly revoked, including explicit default grants. The obsolete unkeyed increment function is revoked from PUBLIC, anon, authenticated **and service_role**. Database owner privileges remain administrative. No table access is widened and no RLS is disabled by the migration. Existing server service-role table privileges are prerequisites, verified on the target before rollout; the service key remains server-only.

The callback accepts GET and POST form data, rejects duplicate/file-valued critical fields, malformed IDs/invoices/amounts/signatures, dual targets and unknown custom `Shp_` parameters. It verifies the original strings using the existing Password2 signature helper. Missing Password2 or Supabase configuration fails closed. Raw signatures and untrusted callback bodies are no longer sent to Telegram. Test notifications are disabled.

## Amount, currency and package contract

`payments.amount_kzt` is the authoritative price snapshot. The numeric RPC compares it exactly with the signed OutSum; current catalog price is not substituted. ResultURL amounts with integer, two-decimal and six-decimal formatting are accepted without rounding. The original string is used for signature verification and passed to PostgreSQL as numeric input.

The integration is Robokassa.kz; the documented merchant OutSum is in KZT. The existing schema has no currency field, and ResultURL does not supply a separate signed merchant currency. `IncCurrLabel` describes the payer's currency and is not used to override the KZT invoice. Confirm merchant/account settings at rollout; this patch does not establish them from production. [Robokassa.kz payment/ResultURL contract](https://docs.robokassa.kz/pay-interface/).

The current schema snapshots `package_id`, **not purchase-time generations**. This patch preserves the existing rule of reading quantity from that referenced package at first fulfillment, then stores the quantity actually credited. Package deactivation or later price changes must not reject a legitimately created invoice. Before enabling callbacks, reconcile pending invoices against their issued offer and freeze package quantities while such invoices can still settle. Do not edit old package quantities in place; future offers can use separate package rows. A purchase-time quantity snapshot requires a separately scoped create-payment contract change; it is not silently assumed here.

## Historical rows: no automatic inference

Adding the nullable receipt intentionally leaves ALL existing paid rows without a receipt. For them `paid` proves neither zero nor exactly one credit: the old flow could have credited zero, one or multiple times. Replays also overwrote `paid_at`. Aggregate user balance and a provider's paid invoice alone cannot prove fulfillment. The migration performs no backfill and changes no historic balance/timestamp/status.

Before rollout, export the affected rows and obtain provider invoice status/amount plus trustworthy per-payment fulfillment logs or equivalent independent evidence. Record the reviewed payment UUID, invoice, user, package/quantity sold, payment status/time, credits already applied, relevant usage/refunds and the evidence used. Do not copy credentials into reports.

Disposition must be approved and executed by an operator in a separate transaction with the payment row locked; recheck its status/receipt under that lock:

1. **Exactly one credit independently proven:** mark `credited_generations` with that proven quantity without changing balance or the original non-null `paid_at`. If the timestamp is missing, resolve it using payment evidence rather than inventing one; until then the RPC continues to reject it.
2. **No credit independently proven:** increment the user's valid balance and record the proven quantity in the same transaction; preserve the original non-null `paid_at`. The normal callback must not be used by resetting historical status to pending.
3. **Duplicate credit proven:** reconcile the excess separately with a reviewed compensation record; do not automatically debit an aggregate balance.
4. **Evidence incomplete:** keep the row unmarked and in manual reconciliation; do not acknowledge it as fully fulfilled or auto-credit it. Provider paid status alone does not distinguish cases 1–3.

`credited_generations` is an application fulfillment receipt, not a historical accounting ledger. Editing it manually without evidence invalidates the safety guarantee.

Keep payment receipts and balances intact; restore the last **safe** application artifact only while the gate stays closed. The old callback is not safe to resume, with or without the legacy RPC grant. A new callback with a missing RPC returns 503 rather than crediting non-atomically.

If the migration has applied but no post-cutover payment writes have occurred, a reviewed rollback may drop only `confirm_package_payment(uuid,integer,numeric)` and the new `credited_generations` column, and restore the captured pre-change ACLs, all while processing remains paused. Restoring PUBLIC execution is not a safe operational state; it is only a faithful pre-change restore while isolated.

If ANY post-cutover fulfillment or manual reconciliation has occurred, retain the receipt column and all data. Do not drop receipts, reset paid to pending, blindly subtract credits or overwrite production with the old full backup: that would lose later legitimate activity or enable duplicate credit. Restore a backup only into an isolated recovery DB, compare records and prepare a reviewed forward repair. Keep callbacks paused until the atomic path and data are verified again.
